# Проект 1C

Данный репозиторий содержит конфигурацию 1С и настройки CI/CD для автоматизации процессов разработки, сборки и развёртывания. 

Архитектура построена на трех независимых процессах:
1. **GitSync** — Выгрузка из хранилища 1С в Git и распределение по задачам.
2. **Build** — Сборка исполняемых файлов (.cf/.cfe) и создание артефактов.
3. **Orchestrator** — Автоматическое обновление продуктивной базы на основе Git-тегов.

---

## Перед началом работы

### Настройка репозитория
1. **sonar-project.properties** — Настройки для анализа качества кода (SonarQube).
2. **extension-prod.json** — Манифест расширений. Используется Оркестратором для проверки обновлений.
   ```json
   {
     "extensions": [
       { "name": "MyExtension", "repo": "https://git.example.com/ext.git", "job": "Build_Ext_Job" }
     ]
   }
   ```

### Структура репозитория
```
project/
├── src/
│   ├── cf/              # Исходники (выгрузка из 1С)
│   └── ...
├── artifacts/           # (Временно) Для хранения скачанных артефактов при деплое
├── extension-prod.json  # Список расширений для PROD
└── ...
```

## 1. GitSync: Синхронизация с хранилищем (Export)

### Назначение
Двусторонняя синхронизация между Хранилищем 1С и Git-репозиторием. Запускается по расписанию. Работает отдельно для основной конфигурации и для каждого расширения.

### Логика работы
1. **Подготовка**:
   - Очистка рабочего пространства.
   - Клонирование ветки `1C_REPO` (служебная ветка, зеркало хранилища).
   
2. **Синхронизация (gitsync)**:
   - `gitsync init` — Инициализация связи.
   - `gitsync sync` — Получение изменений из Хранилища 1С в локальную папку `src/cf`.
   
3. **Push**:
   - Отправка полученных коммитов в ветку `1C_REPO`.

4. **Автоматический Cherry-pick (Task Distribution)**:
   - Скрипт анализирует новые коммиты в `1C_REPO`.
   - Ищет номер задачи в комментарии (формат `#TASK-123` или `TASK-123`).
   - Выполняет `cherry-pick` коммита в соответствующую ветку `feature/TASK-123`.
   - *Автоматическое разрешение конфликтов*: Для служебных файлов (например, `VERSION`) используется версия из коммита.

5. **Фиксация состояния**:
   - Обновление ветки `branch_sync_1c_repo` (маркер последнего обработанного коммита).

## 2. Build: Сборка артефактов (CI)


### Назначение
Компиляция исходного кода в файлы поставки 1С (`.cf` или `.cfe`) и сохранение их как артефактов Jenkins.

### Сценарий: Основная конфигурация (CF)
- **Триггер**: Изменение ветки (например, `develop` или `master`) или ручной запуск.
- **Действие**:
  1. `vrunner compile` — Сборка `.cf` файла из исходников.
  2. **Archive**: Сохранение `.cf` файла в артефактах сборки.

### Сценарий: Расширения (CFE)
- **Триггер**: Webhook (push в репозиторий расширения).
- **Действие**:
  1. `vrunner compileexttocfe` — Сборка `.cfe` файла.
  2. **Versioning**: 
     - Генерация имени тега: `build-{ExtensionName}-{Date}-b{BuildNumber}`.
     - Создание Git-тега и отправка (`git push`) в репозиторий.
  3. **Archive**: Сохранение `.cfe` файла в артефактах сборки.

## 3. Orchestrator: Обновление базы (CD)

**Файл:** `ORCHESTRATOR.groovy`

### Назначение
Умное обновление продуктивной базы данных. Скрипт сам определяет необходимость обновления, сверяя установленные версии (теги) с актуальными в Git.

### Основные параметры
- `DBNAME` — Имя базы данных.
- `MANIFEST_FILE` — Путь к `extension-prod.json`.
- `STATE_DIR` — Каталог, где хранятся файлы с информацией о текущих установленных тегах (`*_tag.txt`).

### Алгоритм работы

#### 1. Проверка обновлений (Check Tags)
- **Основная конфигурация**:
  - Читает последний установленный тег из файла состояния.
  - Получает последний тег из Git-репозитория конфигурации (`git ls-remote --tags`).
  - Если теги отличаются -> помечает флаг `NEED_UPDATE_CF = true`.
- **Расширения**:
  - Перебирает расширения из `extension-prod.json`.
  - Сверяет теги в их репозиториях.
  - Формирует список расширений для обновления `UPDATE_EXT_LIST`.

#### 2. Подготовка к обновлению
- Если обновлений нет — завершает работу.
- Если есть обновления — **Блокирует сеансы пользователей** (`vrunner session lock/kill`).

#### 3. Обновление основной конфигурации (если требуется)
- Копирует артефакт `.cf` из Job-а сборки (`BUILD_CF_JOB`), соответствующий найденному тегу.
- Применяет конфигурацию:
  - Предпочтительно через `ibcmd infobase config apply --force`.
  - Fallback на `vrunner load`.
- Обновляет файл состояния (`cf_tag.txt`).

#### 4. Обновление расширений (если требуется)
- Для каждого расширения из списка обновлений:
  - Скачивает артефакт `.cfe` из соответствующего Job-а сборки по тегу.
  - Загружает расширение в базу (`ibcmd` или `vrunner loadext`).
  - Обновляет файл состояния (`{ext_name}_tag.txt`).

#### 5. Завершение
- **Всегда**: Снимает блокировку сеансов (`vrunner session unlock`).
- Отправляет отчет в Telegram (успех/ошибка).

## Используемые утилиты (v8_utils)

Библиотека `v8_utils.groovy` предоставляет общие методы:
- `cherryPickTasksFrom1CRepo` — Логика распределения коммитов.
- `compileCF_to_file_safe` / `compileCFE_to_file_safe` — Обертки над компиляцией.
- `updateDB_via_ibcmd_or_vrunner` — Умное обновление (попытка ibcmd, затем vrunner).
- `lockSessions` / `unlockSessions` — Управление блокировками кластера.
- `telegram_send_message` — Уведомления.

## Troubleshooting

### Конфликты при cherry-pick
Если автоматический cherry-pick останавливается:
1. Конфликты в `VERSION` разрешаются автоматически (берется версия из коммита).
2. Если конфликт в коде модуля — cherry-pick отменяется для этого коммита, требуется ручное вмешательство.

### Ошибки блокировки
Если база осталась заблокированной после сбоя:
```bash
vrunner session unlock --ras <host>:<port> --db <dbname> --cluster-admin <user> --cluster-pwd <pass>
```

### Orchestrator не видит обновлений
1. Проверьте, что в Git-репозитории создан новый **Tag**.
2. Проверьте, что сборка (Build Job) для этого тега прошла успешно и сохранила артефакты.
3. Проверьте доступность `extension-prod.json` и корректность ссылок на репозитории.
